# ZAVAEBATEL UC — безопасная версия

## Текущий режим и ограничения

- Витрина загружает каталог с сервера; при ошибке поставщика или конфигурации отображается ошибка, а не фиктивные товары.
- Реальные заказы, приём оплаты, платёжные инструкции, загрузка чеков и автоматическая выдача UC выключены. API создания заказов и загрузки чеков возвращает HTTP 503.
- Сервер не создаёт заказы у Nexus и не выдаёт UC автоматически.
- Статические файлы обслуживаются только из `public/`; корневые файлы проекта, включая `.env`, `package.json` и `server.js`, не публикуются.
- Скрипты витрины и админки вынесены в отдельные файлы, чтобы CSP с `script-src 'self'` не блокировала работу интерфейса.
- Административные данные и чеки требуют конфигурации PostgreSQL и входа администратора; изменяющие действия требуют CSRF-токена. В production-cookie сессии включён флаг `Secure`.
- Nexus endpoint, заголовок авторизации, category ID, envelope ответа и поле цены унаследованы от старого кода. Подключение к реальному Nexus не выполнялось; контракт необходимо сверить с документацией поставщика.

## Конфигурация Render

В Web Service → Environment установите:

- `NEXUS_API_BASE=https://nexus.amadeustech.dev`
- `NEXUS_SHOP_ID` и `NEXUS_SHOP_TOKEN` — секреты; задавать только в Render, не в Git и не в логах.
- `NEXUS_PRICE_CURRENCY=USD`
- `NEXUS_USD_RUB=85`
- `SALE_MARKUP=0.20`
- `DATABASE_URL` — только для тестовой/целевой базы после отдельного согласования.
- `ADMIN_PASSWORD` — уникальный пароль администратора.
- `SESSION_SECRET` — случайное значение длиной не менее 32 символов.
- `SBP_ENABLED=false`.

Цена рассчитывается как **цена поставщика в USD × 85 × 1.20**, с округлением до двух знаков после запятой. Значения 85 и 0.20 являются заданными параметрами, а не актуальной рыночной котировкой. Отсутствующая или некорректная валюта блокирует каталог. Ошибки Nexus должны возвращаться без заголовка авторизации и без токена.

Не запускайте production-деплой в рамках этого PR. Сначала настройте отдельное тестовое окружение и проверьте контракт Nexus.

## Маршруты и проверка

- `GET /` — витрина.
- `GET /logo.svg`, `GET /storefront.js`, `GET /admin.js` — статические файлы из `public/`.
- `GET /admin` — страница входа администратора.
- `GET /api/health` — состояние сервера/БД.
- `GET /api/catalog` — каталог либо понятная JSON-ошибка.
- `GET /api/admin/orders` и загрузка чеков доступны только при корректной конфигурации БД и авторизованной админ-сессии.
- `POST /api/orders` и `POST /api/orders/:id/receipt` намеренно отключены.

## Верификация: ограничения этой ревизии

**Проверка тестов в этой среде не выполнена.** Попытка клонировать ветку завершилась ошибкой DNS (`Could not resolve host: github.com`); доступ к npm registry также не подтвердился. Поэтому здесь фактически не запускались `npm ci`, `npm test`, `npm start` или приложение на Render. Не считайте тесты пройденными, пока CI не подтвердит это.

**Блокирующая проблема:** в ветке отсутствует `package-lock.json`, хотя workflow использует `npm ci`. До слияния необходимо в окружении с доступом к npm registry выполнить `npm install --package-lock-only`, проверить сгенерированный lock-файл и закоммитить его, затем выполнить `npm ci && npm test`. Не заменяйте lock-файл вручную неполным файлом и не сливайте PR до успешной воспроизводимой установки.

## База данных и миграции

Не подключайте этот PR к production PostgreSQL для тестирования. Перед любыми миграциями используйте отдельную тестовую базу и резервную копию. Не запускайте миграции, которые изменяют существующие статусы или ограничения, без отдельного плана миграции и проверки совместимости старых данных.

## Что блокирует безопасный запуск продаж

1. Отсутствующий lock-файл и не подтверждённый результат `npm ci && npm test`.
2. Не проверены на реальном поставщике Nexus URL, авторизация, схема каталога, валюта и идентификаторы продуктов.
3. Не проведён тест интеграции с Render и PostgreSQL.
4. Полный процесс заказа, подтверждения оплаты, обработки чеков, возвратов и выдачи UC не реализован и должен оставаться выключенным.
5. Перед открытием продаж нужны отдельные проверки защиты персональных данных, банковских операций, аудита админ-действий и восстановления после ошибок.

## Откат

Не изменяйте production в рамках этого PR. После будущего отдельно согласованного деплоя используйте штатный rollback Render к предыдущему успешному deploy. Не переписывайте историю Git; исправления выпускайте отдельными коммитами/PR.
